# 사내 구매요청서 작성

견적서와 구매 목적을 한국어 구매요청서로 정리한다. 실제 ERP 입력·저장·상신을 요청받으면 아래 브라우저 선택 규칙에 따라 진행한다. 회사 작성 기준은 「260930_구매요청서 작성 방법 안내의 건(ver.1.2)」이다.

**부가정보 탭 비고는 필수다.** `1) 구매목적`, `2) 사용장소`, `3) 관리부서`, `4) 상세내용`의 번호·제목과 실제 내용을 모두 넣는다. 하나라도 빈칸이거나 미확정이면 저장·상신하지 않는다. 품목 행 비고, 첨부파일, 결재 의견글로 대신할 수 없다. 입력을 확정한 뒤 저장 직전 다시 읽고, 저장 후 ERP 재조회와 그룹웨어 본문의 `용도`에서도 네 항목의 반영을 확인한다. 상세 확인 방법은 [브라우저 작업 절차](references/chrome-workflow.md#필수-비고-입력과-반영-확인)를 따른다.

**그룹웨어 첨부는 파일 목록으로 판단한다.** 준비한 파일이 실제 첨부 목록에 등록되고 오류가 없으면 **첨부 완료**다. 이 그룹웨어의 **전송률 0%는 정상 표시**이므로 100% 대기·재첨부·추가 전송이나 첨부 확인용 상신을 하지 않는다. 파일이 누락되거나 명시적인 오류가 있을 때만 해당 파일을 보완한다.

## 작업 범위와 중단 기준

- 사용자가 ERP 작성을 요청하거나 앞서 제안한 ERP 작업에 `진행해`라고 답하면, 그 승인 범위의 입력을 이어간다. 기본정보 몇 칸만 입력하고 최종 응답으로 끝내지 않는다. 저장·상신 권한이 아직 없더라도 검토할 수 있는 품목·수량·금액·비고까지 먼저 준비한다.
- `PI팀 확인`은 분류나 경로가 미확정이라는 뜻일 수 있다. 문의 발송을 명시적으로 요청받지 않았다면 메일 작성창·주소록을 열거나 수신자를 찾지 않는다. 확인할 항목만 기록하고 요청받은 ERP 작업을 계속한다.
- 품목코드를 아직 조회하지 않은 상태와 ERP 조회 후에도 일치 항목이 없는 상태를 구분한다. 확인 가능한 ERP 검색부터 수행한다. 한 품목의 분류·코드가 미확정이면 그 값에 의존하는 입력·최종 저장만 보류하고, 나머지 확정 입력과 부가정보 비고를 끝낸다. 임의 코드로 빈칸을 채우지 않는다.
- 사용자 조치가 꼭 필요해 작업을 멈출 때는 실제 장애, 완료한 범위, 사용자가 해야 할 행동을 한 번에 알린다. 로그인 실패는 아래 로그인 절차를 따르며, 단순 미조회·기본값·미입력을 장애로 보고하지 않는다.

## 먼저 읽을 자료

- 작성·검토 시 [회사 작성 규칙](references/rules.md)을 읽는다. 각 규칙의 원문 쪽수가 표시되어 있다.
- 새 초안은 [결과 양식](assets/output-template.md)에 맞춘다. 사용자가 자료를 준비하려면 [입력 양식](assets/request-input.md)을 안내한다. 이미 받은 정보는 다시 묻지 않는다.
- 화면·표현을 대조할 때만 [원본 안내문](references/source-guide-v1.2.pdf)을 확인한다. 이미지 중심 PDF이므로 필요한 쪽을 렌더링해 읽는다.
- 실제 ERP 입력·저장·상신이 포함된 요청이면 시작할 때 [브라우저 작업과 사전 점검](references/chrome-workflow.md)을 읽고 아래 조건을 먼저 확인한다.

## 실제 작업 시작 전 조건 확인

브라우저 작업이 필요할 때만 Aside 설치·도구와 연결·탭 상태를 확인한다. 별도 지정이 없으면 사용 가능한 Aside를 우선하고, 미설치·비실행·연결 불가면 설치를 요구하지 않고 Chrome의 기존 업무 탭을 재사용한다. 없으면 Chrome에 새 업무 탭을 연다. 사용자 지정 브라우저·탭(읽기 요청의 사이드패널 탭 포함)은 우선한다. Aside의 현재 사용 지침, 권한 거부 시 처리와 전환 전 미저장 입력·첨부·접수 확인은 [시작 전 확인](references/chrome-workflow.md#시작-전-확인)을 따른다.

실제 ERP 작업을 요청받으면 구매정보 질문이나 입력에 앞서 **선택한 브라우저 제어 연결, ERP 로그인 계정과 메뉴 접근**을 점검한다. 그룹웨어 작업(결재 작성·첨부·상신)이 포함된 경우 그룹웨어 로그인과 필요한 로컬 파일 첨부 권한도 확인한다. ERP 입력·저장만 요청받으면 그룹웨어 로그인·첨부 권한은 `해당 없음`이다. 현재 화면·도구가 확인해 주는 사실과 사용자의 설정 완료 답변을 근거로 `확인됨 / 사용자 확인됨 / 확인 필요 / 해당 없음`을 구분한다. 도구가 있다는 이유만으로 로그인이나 첨부 권한을 확인됐다고 쓰지 않는다.

누락된 조건만 짧게 안내하고 사용자 조치가 필요한 항목을 묻는다. 같은 세션에서 확인한 설정은 문제가 생기지 않는 한 다시 묻지 않는다. 필요한 조건이 충족되면 기존 답변을 이어받아 진행한다. 조건을 점검하려고 저장·상신을 실행하지 않는다. 연결을 기다리는 동안 자료 정리는 가능하다. 초안·규칙 설명·정정 방법만 요청받았다면 브라우저 준비를 요구하지 않는다.

**ERP 로그인 화면·세션 만료·인증 실패가 확인되면 즉시 사용자에게 선택한 브라우저의 ERP 탭에서 직접 로그인해 달라고 요청한다.** 작업 탭을 유지하고 로그인 완료 답변 후 현재 계정과 메뉴를 다시 확인해 이어간다. 비밀번호·OTP를 채팅으로 받거나 로그인 문제를 해결하려고 메일·다른 앱으로 전환하지 않는다. 브라우저 제어 도구의 연결·인증 오류는 ERP 로그인 실패와 구분한다. Chrome을 선택했고 탭 목록은 보이는데 선택·포커스만 시간 초과되면 [현재 탭 연결 복구](references/chrome-ui-notes.md#현재-탭-연결-복구)를 먼저 적용하고, 사용자 조치가 필요한 연결·권한 문제만 요청한다. 구체적인 안내는 [시작 전 확인](references/chrome-workflow.md#시작-전-확인)을 따른다.

## 사용자에게 물어보며 작성

기본 진행은 **빠진 정보 확인 → 사용자 답변 반영 → 최종 초안**이다. 먼저 받은 정보를 정리하고, 요청자·소속, 사용·납품, 결재선처럼 관련 있는 항목을 짧은 질문으로 묶는다. 서로 독립적인 주제는 질문 도구의 한 호출에 2~3개까지 함께 물을 수 있다. 긴 입력 양식을 한꺼번에 요구하지 않으며, 불완전한 답변은 빠진 부분만 이어서 묻는다. 사용자마다 달라지는 값은 답변이나 실제 제출 자료를 근거로만 확정한다.

아래 사용자 정보를 기존 답변에서 먼저 정리하고, 각 값을 입력에 사용하기 전에 확인한다. 상신까지 요청받았다면 결재선도 미리 준비하고 결재창에서 실제 조직 검색 결과와 대조한다. 빠진 결재정보는 결재선 입력·상신 단계에서 해결하며 독립된 구매정보 입력을 막지 않는다. 이미 저장된 PRQ의 상신만 요청받으면 현재 단계에서 빠진 결재정보를 확인한다. 초안만 요청받았으면 결재선은 요구하지 않는다.

| 질문 주제 | 사전에 확인할 내용 |
|---|---|
| 요청자·소속 | 성명, 직급, 직책(있으면), 소속 부서·팀·파트명. ERP 구매그룹과 그룹웨어 기안부서는 각각 확인한다. 명칭이 다르면 현재 조직의 팀·파트 관계 또는 기존 사용자 답변으로 대응을 확인하고, 대응이 불명확한 경우만 질문 |
| 사용·관리 | 실제 사용 위치(동·층·실), 관리부서 |
| 납품 | 실제 납품 위치, 사용 위치와 같은지 여부 |
| 결재선 — 상신 요청 시 | 결재 순서별 이름·직급·직책. 소속은 사용자 답변 또는 실제 조직 검색으로 확인하고 동명이인·조직 차이가 불명확하면 질문 |

- 위 정보와 희망 납기, 구매목적/상세사유, 결제방식이 빠져 있으면 그 값에 의존하는 입력만 보류하고 질문한다. 확인된 정보의 정리·ERP 조회·독립된 입력은 이어간다. 고정자산인 경우에만 예산단위·예산계정을 필수로 확인한다. 팀명·인명·직급·직책·장소·날짜·사유를 임의로 만들지 않는다. `희망 납기 없음`은 받은 답변으로 기록하고 다시 묻지 않는다. ERP가 날짜를 필수로 요구하면 현재 기본 날짜를 사용자 확정일로 간주하지 말고 저장 전에 적용 날짜만 확인한다.
- 이번 작업에서 수집한 이름·직급·소속·사용 위치·결재자·계정·PC 경로를 스킬 본문, 예시, 기본값이나 공유 패키지에 저장하지 않는다. 실제 요청서와 해당 건의 첨부에만 확인된 정보를 반영한다. 다른 사용자의 요청에는 그 사용자의 답변을 받으며 이전 요청자의 정보나 결재선을 자동 적용하지 않는다.
- 안내문 예시의 PI팀·통신1센터·요청자 등을 사용자의 정보로 채우지 않는다. 사용장소에서 납품 위치를 추정하지 말고 둘이 같은지 확인한다.
- 공장도 이번 요청의 실제 ERP 선택값을 확인한다. 안내 화면의 `공장명`을 현재 확인값으로 복사하지 않는다. 현재 문서에서 이미 확인된 값은 재사용하며, 미확인 값은 실제 화면·자료에서 확인하기 전 확정하지 않는다.
- 견적서와 답변에 이미 있는 정보는 재사용한다. 서로 충돌하면 어느 값을 사용할지 묻는다. 수량 근거나 교체 사유도 실제 답변에서 나온 내용만 쓴다.
- 질문 도구가 있으면 사용하고, 없으면 대화로 질문한다. 질문을 보낸 뒤에도 승인 범위의 자료 정리·조회·독립된 입력을 이어가고, 답변이 필요한 단계에서 기다린다. 질문을 보냈다는 이유만으로 가능한 작업을 남긴 채 최종 응답으로 끝내지 않는다. 미답변 값을 확정하거나 완성된 요청서로 제시하지 않는다.
- 사용자가 `모름`이라고 하면 확인할 부서/자료를 안내하고 미확정 상태로 유지한다. 사용자가 미확정 항목을 남긴 초안을 원할 때만 `[확인 필요: 항목]`을 넣은 보완용 초안을 제시한다.
- `Default 구매조직`, 요청유형 `구매요청`, 수신부서 `PI운영파트`처럼 **안내문이 정한 고정값**은 규칙대로 적용한다. 사용자 정보와 계산/분류 결과, 고정값을 구분한다.

예: 정보가 전혀 없으면 실제 작업에 필요한 브라우저 준비를 점검한 뒤 `요청자의 성함·직급과 소속 부서/팀/파트명을 알려주세요. 직책이 있으면 함께 알려주세요.`처럼 시작한다. 구매목적/사용장소/관리부서, 결제방식/거래처/금액, 납품 위치/납기/고정자산 예산을 이어서 확인하고 상신 요청 시 결재선도 사전에 받는다. 현재 요청에서 이미 받은 정보는 재사용하고 필요한 값이 모두 주어졌으면 추가 질문 없이 작성한다. 정정 절차나 첨부 목록만 묻는 요청은 그 답에 필요한 정보만 확인한다.

## 작성 순서

1. **경로 확인.** 품목이 일반 구매요청 대상인지 먼저 판단한다. 사무용품·탕비용품·전산비품·안전 보호구·교육비 등 별도 경로는 회사 규칙에 따라 안내한다. 예외에 해당하면 그 근거를 확인하고 진행한다.
2. **자료 정리.** 요청자의 소속·이름·직급·직책, 결제방식, 거래처, 통화, 품목·모델·옵션, 수량, 단가와 VAT 기준, 배송비, 납기, 사용장소, 관리부서, 구매목적을 추출한다. 상신 요청이면 결재자와 순서도 정리한다. 자료 간 충돌과 빠진 값은 사용자에게 순차적으로 질문한다. 필요한 답변을 받은 뒤 초안을 만든다. 사용자가 보완용 초안을 원하면 미확정 값은 `[확인 필요: 항목]`으로 남긴다.
3. **요청서 묶기.** 원칙은 거래처별 한 건이다. 카드결제는 인터넷·현장 모두 ERP 거래처를 `기타거래처`로 지정한다. 여러 사이트의 카드 구매는 이 기준으로 가급적 합치고 실제 사이트/판매자는 품목 옵션과 증빙에 남긴다. 통화나 결제방식이 섞이면 한 건으로 입력 가능한지 확인한다. 전결규정 회피 목적의 분할은 허용하지 않는다.
4. **입력값 결정.** 현금/세금계산서 건은 VAT 별도·해당 거래처·공급가액, 카드 건은 VAT 포함·기타거래처·배송비 포함 최종결제금액이다. 견적 통화를 그대로 쓴다. 배송비는 별도 품목으로 만들지 않고 제품금액에 포함한다. 공통 비용은 근거가 확인된 배분안을 쓰고 합계 일치를 검산한다.
5. **품목별 분류.** 고정자산=고정자산, 판매용 상품=기본계정, 그 밖의 소모품=비용센터 및 E 품목코드. 확정된 소모품은 기본정보와 실제 품목 행의 계정범주를 `비용센터`로 설정하고 계정상세의 실제 비용센터도 대조한다. 화면 기본값 `고정자산`은 변경할 값이며 작업 중단 사유가 아니다. ERP 품목 검색에서 품목명·용도에 맞는 E 코드 후보를 확인하고 명칭·규격·단위를 대조한다. 조회 후에도 분류·코드가 불명확한 항목만 PI팀 확인 사항으로 남긴다. 구매 경로 확인과 회계 분류는 별개이며, 비용센터 선택만으로 별도 구매 경로의 예외가 승인된 것은 아니다. 고정자산은 품목마다 예산단위와 해당 센터 예산계정이 필요하다. 문서 속 예시 계정을 사용자의 계정으로 복사하지 않는다.
6. **내용 작성.** [네 항목 비고 양식](references/rules.md#5-용도-옵션과-비용--p7-9-11-18)에 맞춰 부가정보 비고를 작성한다. 번호·제목을 생략하거나 한 문장으로 합치지 않는다. 수량·시기·대체/증설 사유는 받은 사실로 구체화한다. 품목 행 비고에는 모델·규격·옵션을 별도로 적는다.
7. **저장 전 검토.** 부가정보 비고의 네 항목과 내용이 입력 확정 후에도 남아 있는지 먼저 확인한다. 수량×단가, 비용 포함 합계, VAT/결제방식, 거래처, 통화, 분류/예산, 실제 납품 위치, 납기, 그룹웨어에 첨부할 필수 자료의 준비 상태를 점검한다. ERP에는 파일을 첨부하지 않는다. 금액은 계산기 또는 Decimal 등으로 검산하고 견적 합계와 비교한다. 누락·충돌이 있으면 저장하지 말고 이미 받은 값은 다시 반영하며, 빠진 사실만 질문한다. 사용자가 보완용 초안을 요청한 경우에만 `보완 필요 초안`으로 표시한다. 사용자 정보·품목코드·해당 자산 예산·필수 자료까지 모두 확인됐으면 `입력 가능한 초안`으로 표시한다.

## 결과에 반드시 포함할 내용

- 상태와 확인이 필요한 항목을 먼저 제시한다.
- 실제 ERP 작업은 `미입력 / 일부 입력·미저장 / 입력 완료·미저장 / 저장됨(PRQ) / 상신됨`을 구분한다. `입력 완료`는 모든 요청 품목 행, 수량·단가·합계, 거래처·위치, 부가정보 비고 네 항목과 행 비고가 입력 확정 후 현재 화면에 남아 있음을 확인한 경우에만 쓴다. 기본값 변경·빈 행 추가·입력 도구 성공만으로 작성 완료를 보고하지 않는다. 중단 시 입력된 품목 수/요청 품목 수와 미입력 항목을 명시한다.
- 요청서별 기본정보, 품목 입력표, 복사 가능한 부가정보 비고를 제시한다.
- 첨부자료를 `확인된 자료 / 필요한 자료`로 구분하고 `MRS번호_자료종류_요청품목(거래처명)` 파일명 계획을 제시한다. PRQ 발급 전에는 `[MRS번호 발급 후 치환]`을 쓴다.
- 파일은 **그룹웨어 결재창에서만 첨부**한다. ERP의 파일 첨부 기능은 사용하지 않으며 ERP 첨부 건수를 완료 조건으로 삼지 않는다. 상신 후 실제 첨부는 저장된 그룹웨어 결재문서에서 확인한다.
- 스크린샷 대체가 허용되는 인터넷 소모품 구매는 **가능하면 확인된 옵션·수량대로 장바구니에 담아 캡처하는 방법을 우선**한다. 같은 판매처의 여러 품목을 모아 구매정보가 모두 읽히는 한 장으로 준비하고, 부족한 정보만 추가 캡처한다. 준비 방법과 사용할 수 없는 경우의 대안은 [장바구니 증빙 준비](references/chrome-workflow.md#장바구니-증빙-준비)를 따른다.
- 구매정보 요약용 TXT는 자동으로 작성하거나 첨부하지 않는다. 필요한 견적서·장바구니/상품 캡처 등 분류별 증빙을 첨부하고, 구매 링크는 필요한 경우 결재 의견글에 적는다. TXT 작성은 사용자가 별도로 요청한 경우에만 한다.
- ERP 입력 순서와 저장 후 수정 제한을 짧게 안내한다. 정정 방법만 묻는 요청에는 현재 결재 단계에 맞는 처리 절차만 답한다.
- 기본 결과는 대화의 표와 복사 가능한 문구다. 사용자가 파일 형식을 지정하면 해당 형식으로 만든다.

## 저장된 요청서와 실제 ERP 작업

실제 작업에서는 [진행 상태와 확인 기록](references/chrome-workflow.md#진행-상태와-확인-기록)을 유지한다. 같은 요청을 이어갈 때 확인된 답변·승인·PRQ·결재문서와 단계별 검증 결과를 재사용한다. 브라우저 조작은 [화면별 입력과 복구 방법](references/chrome-ui-notes.md)을 필요할 때 읽어 적용한다. 속도 개선은 질문·조회·실패 조작의 반복을 줄이는 방식으로 하며, 필수 비고와 저장된 첨부 검증은 생략하지 않는다.

사용자가 실행 전 검토를 요청하면 품목·금액·비고 네 항목·첨부·결재선·공개/메일 설정을 하나의 검토본으로 제시하고 승인된 범위에서 이어간다. 같은 내용의 실행 허락은 다시 묻지 않으며, 승인 내용이 달라졌을 때 바뀐 항목만 확인한다.

최종 저장으로 PRQ가 발급된 요청서는 수정할 수 없다. 회사 안내문의 구분에 따라 전자결재 작성 전은 기존 PRQ를 두고 새 요청서 작성, **전자결재 작성 후 완결 전**은 회수 후 **새 요청서 작성**, 완결 후는 구매팀 즉시 연락 후 안내에 따라 조치한다. 미상신 초안에서 회수가 가능한지 불명확하면 현재 문서 상태와 허용된 정정 절차를 확인한다. 회수해 기존 요청서를 수정할 수 있다고 안내하지 않는다.

저장 후 ERP 비고 또는 연결된 그룹웨어 용도에 네 항목이 빠져 있으면 해당 건을 상신하지 않는다. 저장된 ERP 비고가 누락됐으면 위 정정 절차로 새 요청서를 작성한다. ERP에는 정상 저장됐으나 그룹웨어에서만 누락됐으면 연결·전달 문제를 확인하고, 본문에 임의로 덧붙여 ERP 누락을 해결했다고 처리하지 않는다. 정정본에서도 누락되면 추가 PRQ를 반복 발급하지 말고 원인을 확인한다.

초안 작성 요청은 ERP 저장·상신·발주·결제를 수행할 권한을 추가하지 않는다. ERP 조작은 사용자가 요청한 범위와 기존 승인에 맞춰 진행한다. 저장·상신까지 승인된 경우 확정 입력값과 저장 전 점검을 완료하고 진행한다. 승인이 부족한 경우 이미 승인된 범위에서 검토본을 준비한다. 대화 초안 요청이면 대화 안에서, ERP 입력까지 요청했으면 입력 화면까지 준비한 뒤 아직 승인받지 않은 행위만 확인받는다. 저장/상신 결과가 불명확하면 실제 상태와 PRQ를 조회하고, 중복 생성 위험이 있는 재시도는 멈춘다.

상신까지 요청받으면 결재자·직급/직책·순서를 미리 정리하고 결재선 입력 전에 확정한다. 메일 알림·공개 범위는 상신 전에 빠진 값만 묻는다. 과거 사용자의 결재선이나 설정을 새 요청에 복사하지 않는다. 첨부 완료와 실제 상신·접수 상태를 구분해 보고하고, 상신 후 문서번호·결재선·공개 범위·첨부 및 ERP 상태를 [브라우저 작업 절차](references/chrome-workflow.md)에 따라 검증한다.

`종결`은 구매팀 접수 상태다. 구매팀 내부 품의 완결 전 발주할 수 없으며, 구매요청 결재 완료를 발주 완료로 표현하지 않는다.

## 자주 틀리는 부분

| 상황 | 처리 |
|---|---|
| 비고를 입력한 화면만 보고 저장·상신 | 입력 확정 후 네 항목 재확인 → 저장된 ERP 재조회 → 그룹웨어 용도 대조 |
| 품목 행 비고만 작성 | 부가정보 비고의 1)~4)도 별도로 필수 작성 |
| 카드 구매 사이트명을 ERP 거래처로 사용 | 기타거래처로 지정, 실제 판매처는 옵션/증빙에 기록 |
| 카드 금액에 배송비 누락 | 최종결제금액과 대조, 제품금액에 포함 |
| 자산 예산을 요청서 한 곳에만 입력 | 자산 품목마다 예산단위·예산계정 확인 |
| PRQ·품목코드·예산계정이 아직 없음 | 확인 필요로 표시, 임의 생성 금지 |
| 승인된 구매요청을 바로 발주로 안내 | 구매팀 접수 후 별도 구매 품의가 필요함을 안내 |
